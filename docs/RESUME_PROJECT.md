# ResearchFlow 简历与面试材料

## 简历项目名称

**ResearchFlow —— 基于 nanobot Runtime 的可审计论文研究 Agent**

技术栈：Python、aiohttp、SQLite、BM25、FastEmbed/ONNX、RRF、SSE、Docker、GitHub Actions

## 简历项目描述（推荐版）

- 基于 nanobot v0.1.4 的 AgentLoop 与 ToolRegistry 二次开发论文研究 Agent，完成 PDF/Markdown
  语料摄取、BM25 与多语言向量混合检索、证据缺口反思、稳定引用生成及报告引用校验，支持从
  引用回溯到原始证据块。
- 设计 SQLite 持久化异步任务服务与可重放 SSE 事件流，支持任务取消、最大并发 2、进程重启后
  遗留任务恢复标记和项目级研究记忆；提供文档、任务、证据与报告 REST API 及 Web 工作台。
- 构建 40 条中英双语检索评测集和 16 条独立端到端测试集；混合检索 Recall@5 达 0.6500，较
  BM25 提升 20.9%，端到端任务完成率与引用有效率均为 100%；通过 Docker Compose 和 GitHub
  Actions 实现可复现构建与自动测试。

## 一句话版本

基于 nanobot Runtime 构建可审计论文研究 Agent，通过混合检索、稳定引用、异步任务与 SSE
实时轨迹完成端到端研究流程，并以 40 条检索集和 16 条独立问题验证召回与引用质量。

## 面试开场（约 40 秒）

ResearchFlow 是我在读完 nanobot v0.1.4 源码后完成的二次开发项目。原版 Runtime 已经提供了
Agent 循环、工具注册和会话能力，我主要解决的是研究场景中的三个工程问题：第一，回答必须能
回溯到本地论文原文；第二，长任务需要异步执行并向前端实时展示；第三，检索优化不能只凭主观
体验，需要有可复现评测。因此我实现了混合检索和稳定引用体系、SQLite 异步任务与 SSE 事件流，
并建立了检索与端到端两层评测。项目最终可以通过 Docker Compose 一键启动。

## 可深入讲解的技术点

### 1. 为什么不只使用向量检索

BM25 对英文论文中的精确术语表现较强，但中文问题到英文论文的跨语言召回较弱；多语言向量检索
可以补足语义匹配，但首位精确度不稳定。因此系统使用加权 RRF 融合两路排名。40 条评测中，
BM25 Recall@5 为 0.5375，混合检索达到 0.6500。

### 2. 如何保证引用可验证

摄取阶段将每个证据块分配稳定的 `RF-<source>-<chunk>` 标识；生成前先读取精确证据块，生成后
扫描报告中的引用并检查其是否存在，同时计算段落引用覆盖率。前端点击引用会调用精确证据 API，
展示论文标题、页码和原始文本。

### 3. 为什么使用 SQLite

项目是面向个人研究的单机 Agent，SQLite 能同时持久化语料元数据、任务状态、事件和研究记忆，
部署成本低。通过 WAL 模式和最大并发限制控制写入竞争；服务启动时将中断的 pending/running
任务标记为 failed，避免任务永远停留在运行状态。

### 4. 查询反思是否一定更好

不是。当前规则式反思的 Recall@5 从混合检索的 0.6500 提升到 0.6625，但 MRR@5 从 0.5708
略降到 0.5696，耗时约翻倍。这说明它只补回少量深位证据，不应宣传成全面优于混合检索。

## 边界与诚实表述

- 项目是基于 nanobot Runtime 的二次开发，不应描述成从零实现完整 Agent 框架。
- 评测覆盖 6 篇数据流与基数估计论文，不能外推到所有开放领域。
- 端到端评分采用确定性规则而非 LLM 裁判；100% 引用有效率不等同于所有表述均事实正确。
- 端到端生成受模型版本和随机性影响，简历数字以仓库保存的 `e2e-final.json` 为准。
